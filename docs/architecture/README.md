# The architecture page

`index.html` here is a browsable map of Stilo Marker's code, made from the code itself. It starts at the whole system
(the browser's and the server's modules by level, the kernels that start them, what lies between the two ends) and
goes in: a module (its files by layer and which import which), a file (each function drawn with the functions written
inside it, a Python class around its methods), and one function, whose code shows in the pane on the right. Two guides
are drawn from the same data: **How an extension goes in** (`#/guide/extensions`: the folder, the manifest, the module,
what it may use, the examples smallest first) and **How a change goes in** (`#/guide/changes`: the project's rules, its
tests, versions, and this page). Every box can be clicked, and the search finds any module, file or function.

Published with the app on GitHub Pages: https://rustcoleone.github.io/StiloMarker/docs/architecture/

**This page is the project's guideline: after every change, run `python3 tools/architecture.py` and commit
`data.js` and `source.js` with the change.** `tests/architecture.test.py` fails while they are out of date. A file's
opening comment (a docstring in Python) and the comment above each function are the page's text: write them for a
reader.

- `data.js` and `source.js` are generated by [`tools/architecture.py`](../../tools/architecture.py) from every file
  git tracks under `app/`, `server/`, `extensions/`, `desktop/`, `protocol/`, `spec/`, `tools/` and `tests/` (and
  `service-worker.js`; libraries in `vendor/` are left out). Python is read with its `ast`; JavaScript with a reader
  in the tool that knows enough of the language for this (comments, strings, templates and regular expressions, so
  every bracket pairs up). For each file: its opening comment or docstring, its imports, its functions and classes
  (and the functions inside them), the comment above each, which call which, and what it calls in other files.
  A short callback written into an options object (`log: (message) => ctx.log(message)`) is left out unless a
  comment says what it is. The modules come from their own definitions (`defineModule({...})` in a browser module's
  `index.js`, `module.json` on the server, `extension.json` for an extension), the ten rules and the steps to add an
  extension from `docs/ARCHITECTURE.md` and `docs/EXTENSIONS.md`, what an extension may use from
  `protocol/extension-api.json`. Only the top map's fixed boxes are named in the tool (`PARTS`).
- `data.js` holds the structure; `source.js` every file's text, loaded the first time the pane shows code.
- `app.js` decides what each level shows and fills the pane, the search and the trail; the guides' wording is there
  too. `diagram.js` lays the diagrams out with [ELK](https://eclipse.dev/elk/) (elkjs 0.9.3, loaded from a CDN) and
  draws them as SVG: cards with a badge for their kind (M module, E extension, F file, J data, C class, ƒ function,
  § section, K kernel, ▶ what starts things), tinted groups, dotted edges for imports and calls into other files.
  On the top map, a module's uses show while it is hovered.
- Diagrams zoom and pan: scroll or pinch to zoom, drag to move, the − / % / + / Fit buttons, or the keys + − 0 and the
  arrows. `style.css` holds the look, in the app's own colours, light and dark.

**When the shape changes** (a new kind of box on the top map, a new step in a guide), change `PARTS` in
`tools/architecture.py` or the guides in `app.js` in the same commit.

**To read it locally**, serve the repository (`npm start`, or `python3 -m http.server`) and open
`/docs/architecture/` (the diagrams need the internet for ELK).
